## 二、二合一怎么做的

不是"装两个 App 互相跳转"，而是把两个应用**真正打进同一个 APK、同一个进程**里：

1. **代码合并**：CarLife 的 `classes.dex` 保留为 dex1；CarUp 的 3 个 dex 顺延为 `classes2~4.dex`。两边没有同名类，已逐一比对。
2. **资源合并**：CarUp 的 1723 个资源全部并入 CarLife 的资源表。两者原本都用 `0x7f` 且大量撞号，做法是把 CarUp 的条目整体后移到每类资源 `0x400` 之后的空位（CarLife 每个类型最多只用到 `0x78`），然后**把 CarUp 全部 smali 里的资源号常量逐个改写**为新号（2548 处引用，0 处悬挂），重名的 `app_name` 改名为 `cu_app_name`。
3. **清单合并**：权限、`<queries>`、四大组件全部并入；CarUp 的 FileProvider 授权名改为跟随包名（`com.baidu.carlifevehicle.updateprovider`），否则它自更新时会崩；CarUp 原来的桌面入口被移除，只保留一个。
4. **双 Application**：新建 `DualApplication` 继承 CarUp 的 `FreeAutoApplication`（保证 CarPlay 栈、MultiDex、原生库初始化正常），再反射创建 CarLife 的 `CarLifeApplication` 并走完它的 `attachBaseContext`/`onCreate`，让 CarLife 的 `getGlobContext()` 等静态入口继续可用。

## 四、v1.1：方控监听合并

### 4.1 两边的差异

CarUp 的方控链由 `WheelKeySource` 标记来源，原始只有 5 个：

| 来源 | 入口 |
| --- | --- |
| `WINDOW` | `Activity.dispatchKeyEvent` |
| `MEDIA_SESSION` | `MediaSession` 回调 |
| `MEDIA_BUTTON_RECEIVER` | `MEDIA_BUTTON` 广播（静态 receiver） |
| `VOLUME` | 音量变化推算 |
| `BROADCAST` | 运行时注册的媒体按键广播 |

CarLife 则完全不同：`CarlifeActivity.initCustomKeyCodeReceiver()` 按 `CarlifeConfUtil.VALUE_BUTTON_CONTROL` 选一个厂商 Receiver，监听车机 MCU 的私有广播，把字符串/整数键值翻译成自己的 `sendHardKeyCodeEvent(0x10/0x0F/0x1F/0x20)`。

注意这里的 `0x10/0x0F/0x1F/0x20` 是 **CarLife 协议内部的硬键码**，不是 Android `KeyEvent` 键码，不能直接喂给 CarUp。

### 4.2 桥接实现

`src/java/com/shilapi/xcertplay/CarLifeMcuKeys.java`：

- 在 `DualApplication.onCreate()` 里 `install(this)`，动态注册 7 个 action（`android.intent.action.C3_HARDKEY` 被 C3 与奇瑞共用，所以是 7 个 action 覆盖 8 个原 Receiver）。
- `filter.setPriority(1000)`，但不调用 `abortBroadcast()` —— 只旁听，保证 CarLife 通道自己的逻辑不被抢断。
- 解析后统一成 Android 标准键码，分发：
  - 学习页在前台（`WheelKeysActivity.inFront`）→ `logKey(new WheelKeyInput(code, 0, true, WheelKeySource.CARLIFE))` + `onKey(code)`，学习页立刻能显示并记录这个键；
  - 否则 → `CarPlayMediaKeys.INSTANCE.onWheelKey(code, true, false)`，110ms 后补 `onWheelKey(code, false, true)`。
- 开关：`SharedPreferences("dual_wheel").getBoolean("carlife_mcu_bridge", true)`，默认开。

`WheelKeySource` 通过 `tools/patch_wheel.py` 增加第 6 项 `CARLIFE`（label `carlife-mcu`）：改 `clinit` 里的实例构造、`$VALUES` 数组长度（5→6）与索引，已用 `dexdump` 反查确认字节码正确。

### 4.3 键值对照

| 车机 / 方案 | action | 键值字段 | 按下判定 |
| --- | --- | --- | --- |
| 长安（okl） | `com.okl.android.MCU_KEY_IND_ACTION` | `key_value` | `key_state == PRESS_DOWN` |
| 长安（联友） | `com.coagent.intent.action.KEY_CHANGED` | `Key_code` | `Key_state == UP` |
| 长安 C3 / 奇瑞 | `android.intent.action.C3_HARDKEY` | `c3_hardkey_keycode` | `c3_hardkey_action == 0` |
| 吉利 | `com.spd.system.key` | `value` | `state == 1` |
| 阿达优 | `com.adayo.android.MCU_KEY_IND_ACTION` | `key_value` | `key_state == PRESS_DOWN` |
| NWD | `com.nwd.action.ACTION_KEY_VALUE` | `extra_key_value` | 收到即算 |
| 讯飞 | `IKeyClick.KEY_CLICK` | `CLICK_KEY` | `STATUS_KEY == 0` |

| 车机键值 | 标准键码 |
| --- | --- |
| `NEXT`、C3 `0xF3/0xF5`、吉利 `0x14/0x33`、讯飞 `5` | `87` |
| `PREV`/`PRE`、C3 `0xF4/0xF6`、吉利 `0x13/0x32`、讯飞 `6` | `88` |
| `PLAY` | `126` |
| `PAUSE` | `127` |
| `PLAY_PAUSE`、C3 `0xEF`、吉利 `0x12` | `85` |
| `STOP` | `86` |
| `FF` / `FASTFORWARD` | `90` |
| `REW` / `REWIND` | `89` |

### 4.4 为什么要补抬起事件

车机广播只有"按下"这一条。CarUp 的 `perform()` 对带 `hold` 的媒体键（下一首 / 上一首）在按下时记录 `heldMedia` 并发"按下"，抬起时才发"松开"并清零。只发按下会让 CarPlay 端以为按键一直按着（长按快进停不下来）。所以在 110ms 后补一个抬起，等价于一次正常的短按。

## 五、安装

1. 先卸载车机上的原版「百度 CarLife」（签名不同，无法覆盖升级）。
2. 安装 `release/CarLife_Dual_v1.1.apk`。
3. 打开后进入选择页 → 选 CarLife 或 CarUp；退出当前服务会回到选择页，可随时切换。

> 车机把 CarLife 加进"白名单/自启动"（按包名 `com.baidu.carlifevehicle`）的规则仍然有效。

## 六、验证情况

已完成的静态校验：

- `apksigner verify` 通过（v1/v2/v3），`zipalign` 4 字节对齐；
- 资源表 2237 条，smali 中 2548 处资源引用全部命中；
- 4 个 dex 通过 `dexdump`（类数 2118 / 4698 / 535 / 103）；清单里所有 Activity / Service / Receiver / Provider 类名逐项比对，无缺失；
- `WheelKeySource.<clinit>` 反查：6 个枚举实例、数组长度 6、索引 0~5 正确；
- `CarLifeMcuKeys.dispatch()` 反查：`onWheelKey(IZZ)Z` / `logKey` / `onKey` 签名与实际类一致。

**未做的验证**：沙箱内没有 KVM，起不了模拟器，也没有真车机，**没有真机运行测试**。请在实机上确认：

1. 冷启动能否正常进入选择页；
2. CarUp 的 CarPlay、CarLife 的 USB/Wi-Fi 投屏是否与各自原版一致；
3. 方控桥接在你那台车上是否真的收到广播 —— `logcat -s DiPlayCarLifeKeys` 会打印 action、解析出的 keyCode 与 `handled` 结果。

## 七、已知限制

- 两应用共用进程与 targetSdk 25，CarUp 在 Android 12+ 上以"旧目标版本"运行，通知权限等系统提示行为可能与原版略有差异。
- CarUp 只有 `armeabi-v7a` 原生库，64 位车机上以 32 位模式运行（与原 CarUp 一致）。
- 原生库未做 16KB 页对齐，Android 15+ 且强制 16KB 页的车机需要另行处理。
- 方控桥接只覆盖 CarLife 已知的 7 个厂商 action；你的车机若用别家方案，需要按同样方式补 action 与键值表。
- 安装包为自签名；后续版本请沿用同一密钥，否则升级要先卸载。
